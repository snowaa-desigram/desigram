## Purpose

Определяет, что должно быть спроектировано до написания кода: выбор паттернов по каталогу GoF, размещение по слоям и нейминг — чтобы структура кода была предсказуема во всех сервисах проекта.

## ADDED Requirements

### Requirement: Design обязан содержать секцию «Паттерны»
`design.md` каждого change SHALL содержать секцию `## Паттерны`, в которой для каждой новой нетривиальной структуры (новый класс/пакет с поведением, новая точка расширения, новая связь между компонентами) указан либо паттерн из каталога GoF с обоснованием и рассмотренной альтернативой, либо явное «без паттерна — <почему достаточно простого кода>». Выбор паттерна MUST опираться на скилл `gof-design-patterns` (`resources/pattern-selection-guide.md`).

#### Scenario: Change добавляет новую точку расширения
- **WHEN** в design описывается компонент с несколькими взаимозаменяемыми реализациями (например, несколько провайдеров доставки уведомлений)
- **THEN** в секции «Паттерны» назван паттерн (например, Strategy), причина выбора и отвергнутая альтернатива (например, Chain of Responsibility)

#### Scenario: Change — простой CRUD без ветвлений
- **WHEN** новая функциональность укладывается в существующие слои без новых абстракций
- **THEN** секция «Паттерны» содержит запись «без паттерна» с одной фразой обоснования, и это считается выполненным требованием

### Requirement: Design обязан указывать размещение по слоям
`design.md` SHALL для каждого затрагиваемого сервиса перечислить новые/изменяемые файлы с указанием слоя и папки согласно архитектуре этого языка (`architecture-core`, `architecture-go-service`, `architecture-python-service`).

#### Scenario: Change трогает core и Go-сервис
- **WHEN** design описывает новый порт в core и новый RPC в Go-сервисе
- **THEN** для core указаны пути вида `src/<Context>/Application/Port/…`, `Infrastructure/Grpc/…`, для Go — `internal/<name>/{transport,service,store}/…`, и они соответствуют спекам архитектуры

### Requirement: Новые абстракции в Shared требуют обоснования
Добавление в `core/src/Shared` класса с суффиксом `Factory`, `Visitor`, `Strategy`, `Decorator` или нового базового класса SHALL сопровождаться отдельным пунктом в секции «Паттерны» с ответом на вопрос «какую повторяющуюся проблему это закрывает во ≥2 контекстах». Без такого пункта change MUST быть возвращён на доработку.

#### Scenario: Предлагается фабрика репозиториев в Shared
- **WHEN** design добавляет `Shared/Infrastructure/Persistence/RepositoryFactory`
- **THEN** в «Паттернах» есть пункт с ≥2 контекстами, где она нужна, иначе ревью отклоняет change
